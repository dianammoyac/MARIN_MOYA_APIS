# Perfilador público de Raizenta — fase 1

El perfilador está disponible en `/perfilador/` desde la portada `/` y el listado `/inmuebles/`. Reutiliza **exclusivamente `Inmueble`**: `tipo` CASA/APARTAMENTO, `operacion` VENTA, `estatus` DISPONIBLE. Otros tipos, lotes, arriendos y cesiones siguen en el portal, fuera del perfilador. No existe importador ni catálogo adicional. Una publicación individual equivale a una opción; no se promete disponibilidad de unidades.

## Ejecución local comprobada

Requiere Python 3.12 (imagen Docker) o un Python compatible con Django 5.2; la verificación local aquí se hizo con Python 3.14.2 y Django 5.2.17. Desde la raíz del repositorio, PowerShell:

```powershell
py -m venv .venv
& ".venv\Scripts\python.exe" -m pip install -r "requerimientos.txt"
$env:DJANGO_DEBUG='1'
$env:DJANGO_USE_SQLITE='1'
$env:DJANGO_SQLITE_NAME='C:\ruta\a\una\base_de_desarrollo.sqlite3'
& ".venv\Scripts\python.exe" manage.py check
& ".venv\Scripts\python.exe" manage.py makemigrations --check --dry-run
& ".venv\Scripts\python.exe" manage.py migrate --noinput
& ".venv\Scripts\python.exe" manage.py createsuperuser
& ".venv\Scripts\python.exe" manage.py test
& ".venv\Scripts\python.exe" manage.py runserver
```

Abrir `http://127.0.0.1:8000/perfilador/`. **Elegir una ruta nueva para la base local**, no reutilizar una base real; la ruta local utilizada para verificar migraciones fue un archivo SQLite aislado en el directorio temporal. Sin publicaciones elegibles, la pantalla permite responder y muestra «no hay apartamentos o casas disponibles»; no fabrica resultados. Para un recorrido local, el administrador puede publicar un apartamento/casa sintético únicamente en su base aislada; no hay comando de demostración ni precios ficticios en producción.

Con Docker Compose: crear un `.env` privado basado en `.env.example` con `DB_PASSWORD` y `MYSQL_ROOT_PASSWORD` iguales a la contraseña del MySQL de desarrollo, y `DJANGO_SECRET_KEY` propia. El servicio `web` usa Gunicorn y recopila los estáticos al arrancar. Luego:

```powershell
docker compose up -d db
docker compose build web
docker compose run --rm --no-deps web python manage.py migrate --noinput
docker compose up -d --no-deps web
docker compose exec web python manage.py check
docker compose exec web python manage.py createsuperuser
docker compose exec web python manage.py test
```

Los servicios se llaman `web` y `db`. Docker Compose se validó con variables de ejemplo temporales; **el motor Docker no estaba disponible** en la máquina de desarrollo, por lo que no se ejecutaron las migraciones ni pruebas contra MySQL. El contenedor `web` usa Gunicorn, no `runserver`. En un servidor con base existente, no recrear `db`: hacer copia de respaldo, revisar migraciones y actualizar **solo `web`** con `--no-deps`. Ninguna migración se ejecutó sobre producción durante el desarrollo.

## Uso, reglas y supuestos

- La portada `/` redirige a `/index2/`, conservando la configuración pública del dominio ya publicada. El login permanece en `/login/`, registro en `/register/`, paneles y publicación requieren la autenticación que ya tenían. El acceso anónimo al perfilador no concede permisos de publicación. La API previa de inmuebles conserva lectura pública; las escrituras ahora requieren inicio de sesión y solo el propietario o superusuario puede modificar registros; el propietario se asigna en el servidor al crear.
- Cuestionario versión 4: propósito obligatorio **vivir / invertir / vivir e invertir**. Si quien busca vivir no sabe cuántas habitaciones necesita, se pregunta la composición del hogar; invertir pregunta objetivo (arriendo largo plazo, renta corta tipo Airbnb, valorización, reventa o diversificación) con opciones desplegadas en lista y aviso de verificación, horizonte y prioridad, con experiencia y gestión de la inversión opcionales; ambas reúne las ramas aplicables. Estas últimas respuestas aportan contexto para asesoría, no inventan rentabilidad. Ubicación usa un listado **local de departamentos y ciudades de Colombia**, independiente de los inmuebles: se puede dejar abierta la ciudad dentro de un departamento o elegir «sin preferencia» en todo el país. Elegir una ciudad sin anuncios elegibles puede resultar en ninguna coincidencia; no se inventan propiedades. El archivo y su licencia/fuente están en `perfilador/datos/`. Entrega pide los meses deseados o **0 = entrega inmediata** (con botón directo) y admite «No lo sé»; habitaciones y área admiten «No lo sé»; parqueadero admite «Sin preferencia». Cada inmueble declara `modalidad_entrega` (`TERMINADO` / `SOBRE_PLANOS`) y `meses_entrega`; pedir entrega inmediata **excluye** los sobre planos, y pedir N meses puntúa 1 si el inmueble entrega en ≤ N meses o `N/M` si entrega después. La entrega también puede marcarse indispensable. Presupuesto exige monto positivo y moneda COP o USD. El pago ofrece contado/crédito hipotecario o «No lo sé»; no se exige elegir entre pesos y UVR. Recursos preguntan con cuánto cuenta hoy (incluye «No cuento con dinero para la cuota inicial»); cuando son positivos se puede registrar su distribución con montos en cesantías, CDT, cuenta y otros (el porcentaje se calcula solo y debe cuadrar con el total, o declarar «No lo sé»). Ingresos y obligaciones son opcionales y se preguntan si no sabe cuánto puede aportar mensualmente. El aporte mensual pregunta, aparte de lo que ya tiene, cuánto podría sumar cada mes hasta la entrega (sirve para planes de pago por cuotas en proyectos en construcción); si cambia el total de recursos, la distribución anterior se invalida y debe reconfirmarse.
- Las preguntas necesarias no admiten omisión ni «Prefiero después»; las alternativas permitidas se validan también en el servidor. Cada respuesta registra `RESPONDIDA`, `SIN_PREFERENCIA`, `NO_SE`, `PREFIERO_DESPUES` u `OMITIDA` cuando aplique. `NO_APLICA` no se acepta del cliente. Una edición de propósito limpia respuestas de la otra rama; cambiar de moneda obliga a reconfirmar recursos, aportes e ingresos. El **resumen del perfil en la columna derecha** muestra progresivamente lo declarado, incluidos requisitos indispensables y montos con su moneda, y se limpia al iniciar otra búsqueda. Un bloque opcional siempre visible permite ingresar nombre y celular en cualquier momento: el nombre personaliza el título «Perfil de …»; sin nombre se conserva «Resumen del perfil». Estos dos datos solo permanecen en la memoria de la página, sin enviarse a la API del perfilador por esa acción; únicamente si la persona solicita asesoría mediante el formulario correspondiente se remiten como contacto. Las recomendaciones **aparecen y se recalculan automáticamente** después de guardar todas las respuestas necesarias (puede responder «No lo sé» cuando la pregunta lo permita). Al terminar se muestra la recomendación con la opción de **empezar de nuevo**; «Anterior» o «Revisar respuestas» permiten corregir. Cada visita empieza una búsqueda nueva: la página **no retoma respuestas anteriores** y recargarla vuelve a empezar. Hay control de revisión: una actualización antigua devuelve HTTP 409.
- Pesos versionados: para vivir, precio 25, entrega 20, habitaciones 10, área 10, ubicación 15, propósito 10 y parqueadero 10. Para invertir, precio 25, entrega 20, área 10, ubicación 15, objetivo 10, parqueadero 5 y prioridad 15. Para ambas, precio 25, entrega 20, habitaciones 8, área 10, ubicación 15, objetivo 10, parqueadero 7 y prioridad 5. Objetivo, horizonte y valorización/renta no puntúan sin información verificable; la renta corta tipo Airbnb (alquiler por días en plataformas) queda pendiente hasta verificar reglamento y autorización, sin afirmarse por el solo propósito; la prioridad puede reforzar precio, ubicación o área **ya publicados**. La afinidad solo usa criterios verificables: `100 × sum(peso × puntuación)/sum(peso evaluable)`; sin ellos es `null`. Cobertura usa pesos informativos distintos. Estas ponderaciones son hipótesis, no un modelo estadístico validado.
- Precio comparable menor/igual al máximo: 1; de lo contrario, `presupuesto/precio`. Habitaciones y área: `min(1, real/requerido)`. Si no sabe las habitaciones pero sí describe a su familia, se propone **orientativamente** una habitación por cada dos integrantes, redondeando hacia arriba; queda etiquetado como inferencia y no sustituye la respuesta original. Ciudad o departamento: coincidencia exacta ignorando mayúsculas; parqueadero requerido: uno o más registrados. Requisito indispensable **confirmadamente** incumplido excluye incluso si el criterio no suma puntos en la rama de inversión. Desempate: mayor afinidad, mayor peso evaluado, menor precio convertido a COP si es verificable, ID. Aparecen **todas** las coincidencias.
- Los importes se escriben en la moneda elegida y se previsualizan formateados. `ReferenciaCambio` en Django Admin guarda COP por USD, fecha y fuente; solo se usa si es de los últimos siete días, sin consultar internet. Un presupuesto y precio ambos en USD pueden compararse directamente; la ausencia de tasa deja pendientes las **conversiones** entre monedas y bloquea la simulación hasta verificar una referencia; nunca se inventa una tasa. Cálculos internos del crédito siempre son en COP; la presentación se convierte con la tasa documentada y guardada en la evaluación/simulación.
- `Inmueble` declara modalidad y meses de entrega (los sobre planos sin meses quedan **pendientes** de confirmación con la constructora); las terminadas nuevas pueden registrar fecha de entrega por constructora y empresa (opcional), y los sobre planos % inicial exigido y separación (opcionales, pre-rellenan el simulador). Solo los sobre planos tienen meses y condiciones de inicial; las terminadas, fecha. Un usado no puede ser sobre planos (validado). La etiqueta Nuevo con fecha de hace más de 1 año muestra un aviso suave sugiriendo Usado. Carece de inclusiones, fuente verificable del precio y aptitud certificada para invertir: esos datos quedan **pendientes**. El formulario de publicar deriva la modalidad del estado físico (Sobre planos → sobre planos con meses y condiciones; Nuevo/Usado → terminada) sin selector redundante; un "nuevo sobre planos" se publica como **cesión**, que sigue fuera del perfilador. La empresa va en Contacto; crear y editar comparten el formulario. `habitaciones` y `parqueaderos` existentes tienen valor predeterminado cero; para publicaciones antiguas, su exactitud necesita revisión editorial. El estado disponible no equivale a reserva/unidad en tiempo real.
- El porcentaje inicial introducido en la pantalla es **hipótesis**, no condición de un proyecto; los **meses para la inicial son los restantes en vivo** (fecha de publicación + meses declarados, recalculados en cada visita; 0 si es entrega inmediata o ya llegó) y se informa su origen, o los meses deseados si la entrega está por confirmar. La **cuota mensual requerida = (inicial − separación − recursos) ÷ meses** (con 0 meses se paga de una vez); el aporte declarado es capacidad y se compara: `faltante_mensual` y `faltante_total`. El resultado se presenta como **mini-cotización** por filas (inicial, separación, recursos, por reunir, cuota mensual, faltante de la inicial a la entrega, **saldo a financiar a la entrega con su % restante**, cuota estimada banco). Una separación introducida está incluida en la inicial; hitos, cuando los proporcione un servicio, se comprueban en su propio vencimiento. Recursos previstos: recursos aplicables + separación + aporte mensual × meses; plazo cero evalúa inmediatamente. Los importes se calculan con `Decimal` y se presentan redondeados al peso, `ROUND_HALF_UP`.
- Si la persona desconoce su aporte mensual, puede declarar ingresos y obligaciones del hogar y optar expresamente por **explorar el 30 % de sus ingresos** como importe mensual hipotético. Ese porcentaje **no es una regla legal universal**, no descuenta automáticamente obligaciones y no supone capacidad de crédito ni aprobación; los gastos conocidos y pendientes se presentan aparte. La pregunta de cuota cómoda y la de plazo de crédito se retiraron: el simulador calcula la cuota, y el plazo se ajusta allí.
- El hipotecario en pesos usa tasa E.A. decimal: tasa mensual `(1+EA)^(1/12)-1`, cuota fija de capital e intereses. La tasa personalizada se identifica como hipótesis; referencias bancarias se administran en Django Admin, con fuente, verificación, vencimiento y límites. Referencias vencidas no se usan. UVR y leasing requieren simulador diferente. Nunca se interpreta la cuota como crédito aprobado. Seguros, avalúo, escrituración e impuestos no tienen importe oficial en `Inmueble`; se muestran pendientes y **no** se etiqueta el costo como total completo.
- Las evaluaciones guardan respuestas, reglas, precios y explicaciones de su fecha; las simulaciones guardan parámetros, tasa y resultados independientes de cambios posteriores. Al retomar se informa si cambió la publicación. Si cambia antes de simular se exige recalcular. Las solicitudes se confirman después de persistirse y la clave de idempotencia evita duplicados. No se envían mensajes automáticos.

## API y privacidad

`GET /api/perfilador/catalogo/`, `/ubicaciones/`, `/preguntas/`, `/cambio/` y `/referencias/` muestran datos comerciales, departamentos/ciudades, preguntas, tasa de cambio vigente y referencias activas. `POST /api/perfilador/perfilaciones/` crea un perfil; `GET /api/perfilador/perfilaciones/<uuid>/`, `PATCH .../respuestas/`, `POST .../evaluar/`, `POST .../simular/` y `POST .../solicitudes/` verifican la sesión original. Historial propio: `GET .../evaluaciones/<uuid>/` y `GET .../simulaciones/<uuid>/`. Todas las escrituras exigen cookie CSRF y cabecera `X-CSRFToken`. Sin sesión propietaria, un UUID no basta; se devuelve 404. El perfil anónimo sigue accesible tras login **solo con la misma sesión**. No hay listados públicos de clientes. Datos de contacto e ingresos no se incluyen en URLs ni almacenamiento persistente del navegador; la página no conserva el identificador del perfil entre visitas y cada carga crea una búsqueda nueva. Hay límites configurables por acción y hora mediante caché Django; para despliegues con varios procesos configurar una caché compartida antes de depender de los límites operativos.

Las sesiones anónimas pueden expirar por la política de sesiones de Django; una solicitud registrada persiste y se consulta con permiso en Admin. `python manage.py limpiar_perfilaciones --dias 90` **previsualiza** perfiles anónimos sin solicitudes; `--aplicar` elimina únicamente esos perfiles y su historial asociado. No ejecutar `--aplicar` sin revisar la política de retención de datos vigente. `python manage.py clearsessions` limpia sesiones Django expiradas, pero no elimina solicitudes.

## Publicación y datos faltantes

Configurar `DJANGO_DEBUG=0`, una clave secreta nueva fuera del repositorio, `DJANGO_ALLOWED_HOSTS=raizenta.com,www.raizenta.com`, `DJANGO_CSRF_TRUSTED_ORIGINS=https://raizenta.com,https://www.raizenta.com`, MySQL de producción propio, HTTPS, cookies seguras y proxy confiable. En la instancia EC2 revisada, Nginx reenvía las peticiones a `127.0.0.1:8000` con `X-Forwarded-Proto` pero no sirve `/static/` ni `/media/`: Gunicorn atiende la web; WhiteNoise entrega los estáticos reunidos por `collectstatic`, y una ruta de Django mantiene temporalmente las fotos `/media/` cuando `DEBUG=0`. Para mayor eficiencia, migrar luego `/media/` a Nginx sin cambiar sus URLs. Se deben verificar en cada anuncio elegible: vigencia/estatus, valor y moneda, habitaciones, área, parqueadero e inclusiones, gastos/administración, fecha de entrega y condiciones de inicial. Registrar referencias financieras auténticas solo después de verificar fuente y fecha; no se cargó ninguna oferta bancaria.

**Verificación realizada (SQLite aislado, no MySQL):** `manage.py check`, `makemigrations --check --dry-run`, `manage.py test` (45 pruebas), aplicación de migraciones en SQLite local, `node --check` para el JavaScript y validación estructural de Compose con variables temporales. Con el servidor local se verificaron por HTTP `/perfilador/` (200 con `perfilador.js?v=14`), cuestionario versión 4, ubicaciones sin inmuebles y consulta de tasa de cambio (sin tasa verificada en esta base). En Edge automatizado se comprobaron Quindío → Armenia, resumen progresivo (incluida renta corta), personalización opcional del título y limpieza al reiniciar, y recorrido completo sin errores de JS, tanto a 1440 px como a 360 px. También se reprodujo un error de montos incompletos y se verificó que desaparece al completar 30 + 10 + 10 = 50 millones, permitiendo avanzar. Queda pendiente la revisión visual completa en Firefox y la integración MySQL. La gestión por empresas, cálculos UVR/leasing y reservas por unidad corresponden a futuras fases.
